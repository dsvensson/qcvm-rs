# qcvm design

qcvm is a QuakeC virtual machine for engines written in Rust. It runs untrusted, server-supplied
progs, so the design is ruled by three constraints: no `unsafe`, no panics on malformed input,
and a hard limit on every resource QuakeC can grow. Behaviour follows FTE, which is specified in
[spec/](spec) (the VM in [vm.md](spec/vm.md), string builtins in [strings.md](spec/strings.md),
other builtins in [builtins.md](spec/builtins.md)); the deliberate differences are listed in
[deviations.md](spec/deviations.md).

## Layout

```
src/lib.rs          crate docs, re-exports
    opcode.rs       one macro table: the Op enum, opcode names and operand kinds (drives the
                    loader's sanitizer, relocation, the disassembler and the test assembler)
    progs/          Program: loading every format (format.rs, load.rs), .lno files (lno.rs),
                    the disassembler (disasm.rs)
    vm/             Vm<H> (mod.rs), configuration and limits (config.rs), interpreter state
                    (core.rs), the interpreter (interp.rs), memory regions (memory.rs), the
                    QuakeC heap (heap.rs), temp strings and GC (strings.rs), float/int
                    conversions (num.rs), multiprogs (multiprogs.rs), threads (threads.rs)
    builtins/       the Builtins<H> registry and FTE's builtin numbers (numbers.rs, generated by
                    scripts/gen-builtin-numbers.py)
    stdlib/         every builtin that needs no engine, one module per area
    host.rs         the Host trait: everything the VM asks of the engine, all defaulted
    csqc.rs         CSQC helpers (the addentities/predraw walk)
    value.rs        typed handles (EntRef, StrRef, FuncRef, Global<T>, Field<T>, Arg, Ret, …)
    error.rs        VmError, ErrorKind, backtraces, warnings
tests/all/          one integration-test binary (linking is slow on Windows)
tests/qc/           QuakeC fixtures, compiled with fteqcc at test time
benches/vm.rs       criterion benchmarks on assembled programs
```

## Programs

`Program::parse` reads every format FTE accepts — version 6, FTE's version 7 with 16- or 32-bit
records, KK7, uHexen2 and QTest — into one canonical form; compressed progs are rejected. All
counts and offsets are range-checked, so any byte string either loads or yields a `LoadError`.

Statements become `Stmt { op, flags, a, b, c }` with 32-bit operands. Global operands are byte
offsets relative to the program's globals, jump operands absolute statement indices; an
out-of-range jump becomes a sentinel that faults only if it is executed. The loader rewrites
Hexen 2 calling convention calls, and poisons (turns into a faulting opcode) any statement whose
operands lie outside the globals, so the interpreter can trust operands. Malformed function
records are marked invalid and fault when called.

A `Program` is immutable and shared between VMs through `Arc`.

## Memory

Each VM has one byte-addressed space of three regions, all below 2³¹:

```
0          region S: the main progs' strings, its globals (+ zero tail), the local stack,
           then the strings and globals of progs added later
e_base     region E: entity e at e_base + (e << stride_shift)
h_base     region H: the QuakeC heap (memalloc, JSON, base64)
```

Pointers and plain string references are byte addresses, laid out as FTE lays them out, so
string offsets double as pointers and QuakeC pointer arithmetic behaves the same. Entity blocks
have a power-of-two stride with room for fields added later (`ensure_field`, `addprogs`), so
entity data never moves. Every access is bounds-checked; FTE's fallbacks (the `0xFFFFFFFF`
sentinel from `ADDRESS` on a protected entity, pointer access into temp strings) are
reproduced.

Strings are byte strings throughout. Temp strings (`0x8000_0000 | slot`) live outside VM memory
in a slot table; host-interned strings (`0xC000_0000 | index`) are never collected. The garbage
collector is conservative: every aligned word of VM memory with the temp tag, every sleeping
thread and every host pin keeps a temp string alive. It runs only when execution returns to the
host with no QuakeC running, with FTE's trigger.

## Execution

`Vm<H>` owns no host: every entry point takes `&mut H`, and builtins are plain function
pointers `fn(&mut Vm<H>, &mut H) -> Result<(), VmError>`. The interpreter (`interp::run`) does
not depend on `H`. It runs QuakeC-to-QuakeC calls itself and leaves its loop only for a builtin
call, an animation opcode the host may override, a fault, or the return to the host. The generic
outer loop handles those and re-enters. Everything that must survive such an exit lives in
`Core`, so builtins may call back into QuakeC (`Vm::call`) to any depth up to the re-entrancy
limit.

The interpreter keeps the current progs' statements, with global operands relocated to absolute
addresses at load time, in a local; each statement is one dense `match`. Multi-word copies
between globals (`STORE_V`, `RETURN`, parameters) go word by word in order, as FTE's do, so
overlapping operands behave identically; vector copies through pointers read the whole source
first, where FTE's result depends on its C compiler (see the deviations). Float-to-int
conversions and shifts behave as on x86 on every platform.

Errors unwind to the entry of the current host call, restoring saved locals, and carry a
backtrace with source lines when a `.lno` file is loaded. `abort` unwinds to the nearest host
call, which then returns normally. Warnings are buffered and passed to `Host::warning`. A panic
from a host builtin propagates unchanged but leaves the VM poisoned until `reset`. With tracing
on (`traceon`, `Vm::set_trace`) a second instance of the interpreter reports each statement to
`Host::trace` before running it.

## Multiprogs and threads

`Vm::add_progs` loads further progs into a running VM, as `addprogs` does. Each progs has its
own globals; function values carry the progs number in their top byte; entity fields are unified
by name; bodyless (extern) functions are linked by name in both directions; shared globals are
copied whenever execution passes from one progs to another. The new progs' `init(prevprogs)`
runs at once.

`sleep` and `fork` snapshot the running QuakeC call chain — frames, the local stack it uses,
locals, `self` and `other` — and unwind. `Vm::run_threads` resumes due threads (by the `time`
global) when no QuakeC is running; a thread whose `self` was removed meanwhile resumes with the
world instead.

## Builtins and the host

`Builtins<H>` maps names and numbers to functions. `Builtins::standard` registers every standard
builtin under FTE's numbers for CSQC, SSQC or menu progs; hosts add engine builtins with
`set_numbered` and may replace any standard one. Binding happens when a progs is loaded: `#N`
stubs by number, `#0` stubs by name. An unbound builtin faults only when it is called, and
`Vm::unbound_builtins` lists them up front.

The `Host` trait carries everything else the VM or the standard builtins need from the engine:
output, cvars, commands, the clock, files, progs loading, dumps, animation opcodes and spawn
notification. Every method has a default, so a host implements only what it supports.

## Limits

`Limits` bounds everything QuakeC controls: entities, heap, temp strings (count and bytes),
local stack, call depth, re-entrancy, instructions per host call (the runaway counter), progs,
threads, string buffers and hash tables, warnings per call. Exceeding one is an error, never an
abort or an unbounded allocation.

## Testing

- The progs assembler in `tests/all/support/asm.rs` writes every format; opcode tests cover
  every opcode in both record widths.
- QuakeC fixtures in `tests/qc` are compiled with fteqcc and run both here and in FTE's own
  `qcvm` runner, which serves as a black-box oracle (differential tests).
- The csprogs tests run KTX's `csprogs.dat` against a stub engine.
- Property tests feed corrupted progs to the loader, random statements to the interpreter and
  hostile arguments to every standard builtin.
- A repository test checks licence headers and LF line endings.

## Performance

Against FTE's runner, call-heavy code runs at about the same speed and tight arithmetic or
entity-field loops at about 1.5–1.6× FTE's time. Bounds checks and register pressure in the
single dispatch loop account for the difference. The interpreter is much slower unoptimised, so
depending projects should build it with `opt-level = 3` in their dev profile.
